Implemented: the API surface in §3 (including add/remove placement and product edit); tenant-in-partition-key, a central key-builder, and JWKS signature verification (§5); field-level product merge (§6.2); reserved-concurrency bulkheads and opt-in write-sharding (§6.3); OpenSearch search with a DynamoDB off-switch (§6.4); immutable keys, origin shield, and private presigned delivery (§6.5); canary deploys with alarm rollback, reconciliation, and correlation IDs (§7–§8). 01

Requirements and assumptions

A good design answer starts by stating what it's optimizing for — and what it's assuming.

Functional

  • Tenants arrange products onto pan/zoom boards; positions persist.
  • Multiple users edit one board concurrently and see each other's moves in near-real-time.
  • Products carry images; uploads generate derivatives asynchronously.
  • Users browse and filter a catalog of thousands of products per tenant.

Non-functional — the numbers that drive decisions

  • Scale: 500 tenants, 10,000 concurrent users, peaking during synchronized "line review" sessions (~50 people on one board at once).
  • Latency: board load p99 < 300 ms; a peer's move visible p95 < 500 ms; derivatives ready < 30 s (async, tolerant).
  • Availability: 99.9% single-region — not 99.99% (see §9).
  • Consistency: a board's placements are read-your-writes within a session (optimistic locking). Summaries, feeds, and search are eventually consistent, and the UI says so honestly.
  • Durability: never lose a placement; a lost thumbnail is recoverable.

Assumptions, stated out loud

  • Read-heavy: board loads and browsing dominate; writes spike only in line reviews.
  • Tenants are mutually distrusting — isolation is a hard requirement, not a feature.
  • Images are the bulk of storage; records are tiny.
  • One AWS region is acceptable at launch; residency/multi-region is a later, customer-driven ask.
02

Back-of-envelope

Estimate only what changes a decision.

~3M items
500 × 20 boards × 300 placements ≈ 600 MB. Volume isn't the constraint.
~5 TB
2.5M products × (~2 MB original + derivatives). CloudFront is mandatory.
~500 writes/s
Debounced moves, bursty at peak. On-demand absorbs it.
~10k msg/s
Real-time fan-out to peers. This is the scaling story, not the DB.

Access patterns and hot partitions constrain this system — not data volume. One hot tenant at 50k products is the outlier that shapes the catalog design (§6.3), and holding 10k concurrent WebSocket connections open is the outlier that shapes real-time (§6.1).

03

The API contract

For a platform, the interface is the product.

REST for request/response, WebSocket for live updates. Contracts are Zod schemas in a shared package, versioned; consumers are tolerant readers. Tenant is never a request parameter — it comes from the auth token (§5).

GET /api/boards → boards in the caller's tenant POST /api/boards → create board GET /api/boards/:id → BoardView: board + placements + products, 1 round trip POST /api/boards/:id/placements → add a product to the board PATCH /api/boards/:id/placements → batched moves, optimistic-locked (409 on conflict) DELETE /api/boards/:id/placements/:pid → remove a placement GET /api/boards/:id/events → activity feed, newest first POST /api/products/:id/assets → presigned upload (bytes go browser→S3) PATCH /api/products/:id → edit a product (field-level merge) GET /api/catalog?filter=... → search / filter (OpenSearch, or DynamoDB when off) WS /realtime (subscribe boardId) → PlacementMoved, PlacementAdded, PlacementRemoved
04

Architecture & the primary request paths

Same shape as today, scaled: CloudFront (static app + /api/*), API on Lambda behind an HTTP API, single-table DynamoDB with Streams, EventBridge, the media service — plus, new at this scale, an API Gateway WebSocket tier, a connection registry, and an OpenSearch read model.

Board load — GET /api/boards/:id

One Query returns the board #META plus its placements (the item collection as a precomputed join); a BatchGet then hydrates products. p99 < 300 ms — measured at 77 ms for 200 placements locally.

Tile move — the real-time path

Client moves optimistically → debounced PATCH → conditional TransactWrite (optimistic lock) → the DynamoDB Stream emits the change → the stream consumer writes the change-event (transactional outbox) and publishes PlacementMoved to EventBridge → a fan-out Lambda pushes to each peer's WebSocket. The mover already sees their own change; peers see it p95 < 500 ms later.

Image upload

POST …/assets returns a presigned URL and emits AssetUploadRequested; media records the pending asset, processes on ObjectCreated, emits AssetProcessed; the API applies it to the product. Fully async — the board renders placeholders until derivatives land.

05

Multi-tenancy

Decision

Pooled, not siloed. One table, tenant encoded in the partition key (TENANT#<t>#BOARD#<id> — now implemented for the board aggregate; products remain PROD#<id>). A table or stack per tenant is rejected at 500 tenants — it multiplies operational surface and deploy risk by tenant count for isolation a scoped key already gives.

Isolation, defense in depth:

  • Tenant comes from the token, never the request. The tenantId claim is injected server-side into every key; a client can't ask for another tenant's board because it can't name the partition.
  • This is the BOLA class (Broken Object Level Authorization) — the most common API vulnerability. No code path lets a URL id select a partition on its own.
  • IAM session policies as a second layer: handlers assume a short-lived role with a dynamodb:LeadingKeys condition pinned to the tenant, so even a logic bug can't cross tenants at the AWS level.
Tradeoff

Every query must carry the tenant prefix; a forgotten prefix is a bug class — so it's centralized in one key-builder module and covered by tests.

06

The hard problems

A decision and a tradeoff for each.

6.1 · Real-time collaboration

Decision

API Gateway WebSocket + a connection registry in DynamoDB (CONN#<boardId> items with a TTL so dead connections self-evict). On PlacementMoved, a fan-out Lambda posts to each connection. Reconnect: the client re-fetches the board, then resubscribes — the socket carries deltas, not truth.

Tradeoff

Fan-out is O(viewers) per write; a 200-viewer board is a hot fan-out. Mitigate by batching deltas per board per ~100 ms and sharding fan-out by connection range. OT/CRDT sync is unnecessary while LWW positions are acceptable.

6.2 · Concurrent editing

Decision

Keep optimistic locking with last-write-wins for positions (already built). Same-tile collision: one wins, the loser's client reloads. For non-positional fields (name, price), field-level merge.

Tradeoff

LWW can lose an in-flight drag on a rare same-tile collision — cheap and correct enough for spatial arrangement. CRDTs would make every edit mergeable but add real client/server complexity; unjustified until customers report conflict pain.

6.3 · Hot tenants and hot partitions

Decision

The bulkhead pattern — isolate blast radius by tier: separate SQS queues and reserved Lambda concurrency per tenant tier, so one tenant's bulk import can't starve others. For the 50k-product tenant: paginated catalog via GSI, and write-sharding a hot board's partition if it exceeds a partition's throughput.

Tradeoff

Sharding complicates reads (scatter-gather) and is only worth it for proven hotspots — apply per-board, by evidence, not everywhere.

6.4 · Search and filtering

Decision

OpenSearch fed by DynamoDB Streams. Twenty arbitrary filter combinations is not a key-value access pattern; forcing it into DynamoDB means scans or a GSI per filter. Streams project products into an index; the catalog route queries OpenSearch.

Tradeoff

A second datastore to operate, and eventual consistency — a just-edited product may lag in search by seconds. Acceptable for browse; DynamoDB stays authoritative.

6.5 · Image delivery at scale

Decision

CloudFront over the S3 derivatives, immutable caching (the key contains a UUID, so content never changes), origin shield to collapse origin fetches. Private-tenant assets use signed URLs.

Tradeoff

Cache invalidation is a non-issue by design, but per-tenant signed delivery adds URL-signing on the read path — batch-sign at board load.

07

Failure modes

What breaks first, and the blast radius.

  • A viral board overwhelms fan-out before the DB → back-pressure deltas, shard fan-out, degrade to interval-poll if the socket tier saturates.
  • DynamoDB hot partition on one board's writes → write-sharding; meanwhile throttles return 429 and the client's debounce retries.
  • OpenSearch falls behind the stream → search is stale, browse still works, the DB remains authoritative; alarm on iterator age.
  • Media outage → uploads still succeed, boards render placeholders, images appear on recovery (graceful degradation). DLQ + alarm.
  • Bad deploy → bounded by canary/gradual Lambda deploys with automatic rollback; a media bug can't take down boards.
  • Consumer breaks for a day → reconciliation rebuilds the drifted read models without replaying an expired stream.
08

Operations

  • Deploy: CDK, two stacks (core + media), gradual traffic shifting with alarm-based rollback. Same-origin via CloudFront — no CORS, first-party cookies.
  • Capacity: DynamoDB on-demand at launch; switch hot tables to provisioned + autoscaling once traffic is predictable, for cost.
  • Migrations: single-table is rigid — additive attributes are free; new access patterns need a new GSI or a Streams-driven backfill. Never big-bang.
  • Monitoring: DLQ depth > 0, stream iterator age, API 5xx / p99, DynamoDB throttles, reconciliation discrepancy count, connection count and fan-out latency. Alert on symptoms ("board load failing"), not causes ("CPU high"). Correlation IDs cross every async hop.
  • On-call: runbooks keyed to each alarm; the DLQ is the first place to look.
09

What to defer, and why

Right-sizing is the senior signal. Naming the exit ramps matters more than building them.

  • Multi-region active-active. 99.9% in one region meets the target; active-active triples cost and forces conflict resolution on global writes. Revisit when a contract demands 99.99% or data residency.
  • CRDTs / OT. LWW positions are acceptable; adopt only if real conflict pain appears.
  • Per-tenant tables. Only for a regulated customer needing physical isolation; pooled keys + IAM cover the rest.
  • A service mesh / more splits. Two services is the right number; more would be a distributed monolith. Split further only on evidence of divergent scaling or ownership.
  • GraphQL / a BFF. REST + WebSocket is sufficient; add aggregation only if client round-trips become a measured problem.

Proposing global active-active and CRDTs for a fifty-person company is enthusiasm, not judgment. This design scales to the stated numbers and names where to change course when they change.
